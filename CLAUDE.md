# six7swe

Portfolio + job-matching SWE platform. Full architecture in `docs/architecture.md`.

## Architecture Notes
- Two separate products in one repo: the public **portfolio** (landing content is static in `frontend/src/content/`; routes in `backend/src/routes/portfolio.ts`, no database tables) and the **job hunter** (`backend/src/db/schema/jobHunt.ts`, routes in `backend/src/routes/jobHunt.ts`). The job hunter lives under `/job-hunt/*` and is the only part of the backend that needs `DATABASE_URL`.
- Auth verifies real Supabase JWTs against the project JWKS (`backend/src/services/auth/`). Routes are private by default and opt out via `PUBLIC_ROUTE` in `backend/src/routes/access.ts`. `AUTH_DEV_BYPASS=true` is for local use only.
- Supabase used for Storage only (resume/PDF bucket `portfolio-files`); no frontend Supabase client
- **Migrations.** The schema (`backend/src/db/schema/`) is the source of truth. `pnpm run db:generate` writes a migration from a schema change; `pnpm run db:migrate` applies it. `pnpm run db:reset` rebuilds the database from the migration history.
- **`pnpm run db:reset` leaves the database empty.** Dev data is opt-in with `--seed` (job hunter users and profiles only). A reset against the hosted database asks you to type the host before it drops anything (`--yes` skips the prompt).
- **`auth_id` is the identity key, not the email.** A local user row is bound to exactly one authenticated subject and is never re-bound (`backend/src/domain/jobHunt/identity.ts`). `users.email` is nullable because a token may carry no email claim.
- **The landing page is static.** Its content and contact details live in `frontend/src/content/` (edit by hand; a null field in `contact.ts` hides its row). There is no `/portfolio` route. `/resume` serves only the knowledge service's primary resume, cached by corpus version (`backend/src/services/resumeDownload.ts`), 404 when none. The contact form delivers to `CONTACT_TO_EMAIL` (503 when unset).
- **Retrieval is the only background source.** Chat (`backend/src/data/chatContext.ts`), fitcheck (the job description as the query) and the job hunter (`backend/src/services/jobHunt/knowledgeSource.ts`: per-job retrieval plus one fixed overall-background retrieval) all answer from knowledge-service retrieval. There are no portfolio tables, no published profile and no `PORTFOLIO_DATA_SOURCE`; `KNOWLEDGE_URL` and `KNOWLEDGE_SERVICE_KEY` are required in production. When retrieval is down, chat says the background is unavailable and fitcheck answers 503.
- **Background caches are keyed to the corpus version (`/version`), never busted in process.** An upload or delete moves the version, so every replica picks it up: chat/fitcheck retrieval and `/resume` re-read the version at most every 30 s (`DEFAULT_VERSION_TTL_MS`); the job hunter reads it at the start of every run (`backend/src/services/knowledge/versionKeyedCache.ts`).
- Lerna was removed: it was never used, and it pulled in `nx` and `axios`, which accounted for most of the dependency advisories. pnpm workspace scripts are authoritative
- `packages/knowledge-types` (`@six7swe/knowledge-types`) holds the knowledge wire contract (Zod schemas and constants) shared by the backend and the knowledge service. It compiles to CommonJS `dist/`, which `pnpm install` does not build: consumers' scripts build it first, and `pnpm build:types` rebuilds it after editing
- **Knowledge service** (`knowledge/`): a separate ESM deployable. It holds the owner's background docs and serves vector retrieval (pgvector) for chat, fitcheck and job matching, plus the primary resume PDF; see `knowledge/README.md`. It owns the `knowledge` + `knowledge_migrations` Postgres schemas and never touches `public`. Its migrations are applied with `pnpm --filter @six7swe/knowledge db:migrate` (not drizzle-kit migrate, which swallows errors). `EMBEDDER=hashing` + `FILE_STORE=local` run it offline.
- **Knowledge owner gate is in the backend.** The service stays private-network only. The owner's page (`/hunter/knowledge`) calls the backend's `/knowledge/*` proxy (`backend/src/routes/knowledge.ts`), which checks `sub === OWNER_AUTH_ID` (403 otherwise) and forwards with `KNOWLEDGE_OWNER_KEY`, never the user's token.
- **The public MCP server is the backend's `POST /mcp/public`** (#205; `backend/src/routes/publicMcp.ts`), not the knowledge service's `/mcp` (the owner's private one): `search_background` and `get_resume_pdf`, no auth, rate limited per client, and searches capped per UTC day in process memory (one replica). Each search is recorded in the eval set as its own session.
- **Chat examples live in `packages/knowledge-types/src/chatExamples.ts`** (at most 6; a test keeps the pool at or below the eval active size minus 4). The frontend compiles that module from source via an alias; the knowledge service seeds each as a pinned eval question, and a click (`/chat` with `example: true`) bumps only its `example_clicks`.
- **Railway config is `.railway/railway.ts`** (Infrastructure as Code; `railway.json` was retired before the 2026-12-01 cutoff). Railway does not read it on deploy: a change is applied by hand with `railway config plan` then `railway config apply`. Applies are declarative, so a variable missing from the file is deleted; secrets are listed as `preserve()`.
- **On Windows, `railway config plan` / `railway config apply` fail** with "This version of railway/iac requires Railway CLI 5.42.1 or newer" even on a current CLI (5.74.0). The `railway` SDK checks the version by running `railway --version` without a shell, which cannot spawn the `railway.cmd` / `railway.ps1` / `railway` shell shims that npm and pnpm install. Fix: put the directory holding `railway.exe` ahead of the shims on `PATH` — `$env:PATH = "$(npm root -g)\@railway\cli\bin;$env:PATH"` (PowerShell; cmd.exe and Git Bash variants, and how `_` factors in per shell, in [Changing Railway config](./DEPLOYMENT.md#changing-railway-config)).
- **Pull requests close their issue.** Put `Closes #<n>` on its own line at the top of the PR description; a bare `(#123)` reference only links it and leaves the issue open after the merge. The full rule is in `.github/copilot-instructions.md`.
